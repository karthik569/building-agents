The loop is the agent

Everything you have heard called an "agent" is one loop. In this session you will read that loop until it stops being impressive, run it offline for free, and then break it in four ways so you know exactly what it does when it fails.

90–120 min, hands-on No API key needed Two real bugs to find
You leave able to

Write an agent loop from scratch in ~50 lines, name every part of it, explain why an error must be returned as content instead of raised, and say what a step cap is protecting you from — without looking anything up.

Why this first

You are going to ship an agent at work. The failure mode that kills those projects is not "the model wasn't good enough." It is the 80% trap: a demo that thrills in a review and then collapses in week two, because the last 20% lives in the control flow, the error paths, and the evals — and a framework hid all three from you.

Dex Horthy interviewed roughly a hundred builders and found the same shape repeatedly: grab a framework, reach 70–80% quality, discover 80% is not shippable, then reverse-engineer the framework to find the missing 20% and end up rewriting from scratch (12-Factor Agents). The cheapest insurance against that is to build the thing once, by hand, on a task small enough to finish today.

So we start at the bottom. Not because frameworks are bad, but because you cannot debug what you did not write.

The claim, stated plainly

An agent is a loop over three moves. Anthropic calls this "LLMs using tools based on environmental feedback in a loop" and notes the implementation "is often straightforward" (Building effective agents). Thorsten Ball built a working code-editing agent in under 400 lines and titled the piece The Emperor Has No Clothes (Amp). 

messages = [system_prompt, user_task]

for step in range(MAX_STEPS):
    turn = model.complete(messages, tools)   # 1. ask
    messages.append(turn)

    if not turn.tool_calls:                  # 2. done?
        return turn.text

    for call in turn.tool_calls:             # 3. act
        result = execute(call)
        messages.append(result)              #    and observe

return TIMEOUT

That is the whole architecture. A planner is this loop with an extra prompt. An executor is the execute line, extracted. A graph is this loop with the branches written down. Multi-agent is this loop calling itself. None of those are wrong — but each is a decision you should make against a failing trace, not on day one.

The one sentence to remember

The model does not do anything. It returns a tool call — a structured request — and your code decides whether to honour it. Every guardrail you will ever build lives in that gap.

What you are going to build

There is a working lab at lab/ in this workspace. It is deliberately small: a types module, a tool registry, two models, and the loop.

Two models, one interface. ScriptedModel makes decisions by reading the conversation with rules instead of weights. That is not a mock — a mock asserts "I expected exactly these calls", which breaks on every harmless prompt edit and proves nothing. A scripted model asserts "given this conversation, a competent agent would do X", which is the property you actually want to hold. It also means every lab in this course runs offline and costs nothing, so you will never be tempted to hand-test in place of writing a test.

Step 1 — watch the loop work

From the workspace root:

# offline, deterministic, no key, no cost
python3 lab/run.py --task "Summarise the release checklist"

You should see something close to this:

TASK  Summarise the release checklist
STATUS done  STEPS 3
--------------------------------------------------------------------
[1] model   (no text)  0ms
          -> list_files({"path": "$REPO/lab/sandbox"})
[1] tool     list_files => notes.txt\nrelease-checklist.txt
[2] model   (no text)  0ms
          -> read_file({"path": "$REPO/lab/sandbox/release-checklist.txt"})
[2] tool     read_file => Release checklist — Q3\n============...
[3] model   Done. Saw 2 file(s). First lines: Release checklist...
[3] stop    final_answer
--------------------------------------------------------------------

Read what happened, because it is the entire lesson. The model was never told about release-checklist.txt. It was told the task and given a tool inventory. It chose to list, saw two files, chose the one whose name matched the task, read it, and stopped. Nobody wrote "if the user mentions a checklist, read the checklist file." That decision came from the model, at runtime, from the tool descriptions.

That is the difference between a workflow and an agent, and it is the first thing you should be able to point at.

Step 2 — read the loop out loud

Open lab/agentlab/loop.py. It is about fifty lines of body. Read it twice. Then answer these from memory, out loud, before scrolling:

  1. Where does the system prompt go, and why is it first?
  2. What exactly makes the loop stop?
  3. Why is the tool result appended as a Message rather than returned?
  4. What happens if the model asks for two tools in one turn?
  5. What is max_steps protecting?

If any of those felt shaky, you have found the thing to fix before moving on. Ask me — that is what I am here for.

Step 3 — break it, on purpose, four ways

An agent you have only seen succeed is an agent you do not understand. The tests in lab/tests/test_loop.py encode the four failure modes worth knowing. Run them: 

cd lab && python3 -m unittest discover -s tests -t . -v

Twelve tests, fifteen milliseconds, zero cost. Now read what they assert:

01

An unknown tool does not crash the run. The model hallucinates delete_everything. The registry returns an error string, which goes into the conversation, and the model gets a chance to recover. If you had raised instead, the run would die and the model would learn nothing.

02

A tool that throws does not crash the run. Same principle one layer down: the boundary catches, formats, and returns. Note it distinguishes ToolError (expected: bad path) from everything else (a bug in your code). Without that distinction you end up sniffing strings for "Error:", which works right up until someone's file is named Error:.

03

A looping agent is stopped by the cap, not by hope. The test feeds fifty identical list_files calls and asserts the run stops at three. This is the cheapest guardrail you will ever write, and the one most often left out.

04

Relative paths are rejected. Not discouraged — rejected, with a message that hands back the absolute path. Anthropic's team found during SWE-bench that models fumble relative paths after moving directories, and fixed it by requiring absolute paths. They call it poka-yoke: remove the failure mode rather than documenting it.

Step 4 — the bug I actually hit

This lab was not written perfectly, and the imperfection is the most useful thing in it. The first version had this line in the scripted model: 

# track which files we have read
read.append(str(c.args.get("path", "")))     # "/abs/path/notes.txt"
...
# later, compare against the bare filename
if target not in read:                       # "notes.txt" — never matches

Full path on one side, basename on the other. The membership test could never succeed, so the agent re-read the same file until it hit the step cap. The trace looked like a model that would not stop; the cause was a string comparison two files away from where the symptom appeared.

The lesson in that bug

Almost every "the model is being dumb" bug is a bug in your code, your tool description, or your context. Read the trace before you touch the prompt. When you do reach for the prompt, remember its errors are prompt text — an error message that does not say what to do next is a wasted turn.

Reproduce the shape of it yourself: run with a two-step budget and watch it stop mid-task. 

python3 lab/run.py --steps 2

STATUS max_steps. The run ends with a partial answer and, crucially, a trace that says where it was cut off. That is what a good failure looks like: boring, bounded, diagnosable.

Step 5 — go live, when you have a key

The same loop, a real model, no code change beyond the flag: 

export OPENAI_API_KEY=...
python3 lab/run.py --live --task "Summarise the release checklist"

Everything you learned offline still holds; only the decision-maker changed. This is the payoff of the Model protocol: the loop does not know or care whether decisions come from weights or from rules.

Check yourself

Answer before clicking. The point is retrieval, not recognition — guessing and being wrong here is worth more than rereading the page.

01What ends an agent loop in the lab?

Why: A turn with no tool calls is the model's claim that it is finished. That is the only success exit. The step cap is the other exit, and it is a failure. Text can be empty while tool calls are present; check the calls, not the prose.

02A tool raises FileNotFoundError mid-run. What should the loop do?

Why: Errors are results. Returning them as content lets the model read the failure and change approach on the next turn — factor 9 of 12-Factor Agents, "compact errors into the context window". Raising kills a run that was one turn from recovering; retrying identically reproduces the same failure; dropping it silently makes the model confidently wrong.

03Your agent succeeds with two tools today. A teammate proposes twelve more and a planner. Best next step?

Why: Anthropic's rule is to add complexity only when it demonstrably improves outcomes, and Horthy's is to adopt a pattern against a failing trace. More tools raise capability and lower reliability at once; without a failing case you cannot tell which happened. "It works, so let's make it bigger" is how projects reach the 80% trap.

04Why does read_file reject relative paths instead of resolving them?

Why: Poka-yoke. Anthropic found models failing with relative paths after directory changes and fixed it by requiring absolute ones — "the model used this method flawlessly". The error message then hands back the absolute path, so the next turn can succeed. Making misuse impossible beats writing more instructions about it.

05A run ends STATUS max_steps with a partial answer. What do you inspect first?

Why: Two very different causes, one symptom: thrash (repeated identical or failing calls) versus a genuinely larger task (cap too low). The trace distinguishes them instantly and nothing else does. Raising the cap on a thrashing agent just buys a larger bill; chasing the prompt on an under-budgeted agent just wastes a day.
